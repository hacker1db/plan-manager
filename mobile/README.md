# Plan Manager mobile (Expo / React Native)

iPhone, iPad and Android client for the hosted Plan Manager. Expo SDK 58, React Native 0.88, Expo Router. It reads the owner's hosted library and can change a plan's hosted status; the canonical vault is never changed from the phone.

## How it fits with the web app

- **API:** the existing REST routes under `/api/v1/plans` (list, `render`, `content` for annotate mode, `status`). There is no separate mobile backend.
- **Shared contract:** `src/lib/shared.ts` imports the web app's dependency-free `src/lib/types.ts` and `src/lib/hosted/types.ts` (`PLAN_STATUSES`, `DashboardPlan`, `PlanListResponse`, `PlanRenderResponse`). The server routes check their responses against the same types with `satisfies`, so a contract change fails both typechecks. Keep those two files free of runtime dependencies; `metro.config.js` watches `../src/lib` so Metro can bundle them.
- **Auth:** WorkOS AuthKit public-client PKCE (`src/lib/auth.ts`, the same endpoints as `workos-ios` 0.9.0). The access token is sent as `Authorization: Bearer …`. The server accepts it only when `PLAN_MANAGER_WORKOS_NATIVE_CLIENT_ID` is set; see `docs/hosting.md`, "Native app access".

## Look and feel

- **Theme:** dark only, like the web app. `pnpm sync-theme` regenerates `src/theme/web-theme.generated.ts` from the web's `src/dashboard/style.css`: the resolved `:root` tokens for native screens, plus the web's `.markdown-body` and `pm-*` rules for the plan reader, so plans render as they do on the hosted site. `test/theme.test.ts` fails if the generated file is stale. `app.config.ts` reads the same tokens for the launch background.
- **Icons:** `pnpm generate-icons` derives the iOS light, dark and tinted icons (iOS 18+ Home Screen appearances) and the Android adaptive-icon layers from the web's `src/dashboard/icon.png`.

## Comments to T3 Code

The plan page shows the rendered plan with a **+** beside every block: headings, paragraphs, list items, code blocks and tables. Tap one and write what should change. Comments appear inline in the page (tap one to edit or delete it) and stay in memory on the phone, per plan, until you clear them or sign out. **Open in T3** builds a prompt and opens a T3 Code prompt link: `t3code://new?…`, falling back to `https://app.t3.codes/new?…`, with `repo=$PLAN_MANAGER_T3_REPO` (default `hacker1db/SecondBrain`). T3 opens a prefilled thread in your most recently used project for that repo, and **nothing is sent until you press Send in T3**.

Each comment is anchored by its block's rendered text, block kind and nearest heading, rather than a line number. The prompt quotes all of these, along with the plan ID and the hosted revision, and tells the agent to run `plan show`, then `plan update --stdin --if-revision` (never force), then `plan push`. When the new revision reaches the hosted copy, the plan screen says the plan changed since your comments. Comments re-attach to a block only when exactly one block has the identical text; the rest are counted in a banner and still included when sending. T3 prompt links accept up to 8,000 characters; longer prompts are refused before opening.

**Security trade-off:** the **+** buttons need a script in the reader, so the WebView runs JavaScript. The only script that runs is the app's own annotator (`src/lib/annotator.ts`), injected natively, which page CSP doesn't apply to. The page CSP (`default-src 'none'; script-src 'none'`) still blocks every script, inline handler and `javascript:` URL in the plan HTML. The annotator inserts comment text with `textContent`, never as HTML. Messages from the page are schema-validated before the app acts on them. `test/annotator.test.ts` runs the exact injected script in jsdom.

## Setup

```sh
cd mobile
pnpm install
cp .env.example .env.local   # fill in the WorkOS client ID; none of these values are secret
```

In the WorkOS dashboard, add the exact `PLAN_MANAGER_WORKOS_REDIRECT_URI` (default `dev.hacker1db.planmanager://callback`) as a redirect URI. The URI scheme becomes the app's URL scheme, so changing it requires a native rebuild.

## Run

The custom-scheme sign-in callback needs a development build. Expo Go can't receive it, so it only works for fixture previews.

```sh
pnpm ios                                       # simulator dev build (expo run:ios)
pnpm exec expo run:ios --device <UDID>         # your phone over USB (`xcrun devicectl list devices`); signs with PLAN_MANAGER_APPLE_TEAM_ID
PLAN_MANAGER_FIXTURES=1 pnpm ios               # labeled offline sample data, no sign-in or network
```

`ios/` and `android/` are generated by `expo prebuild` and are git-ignored. The first device build for a new bundle ID needs Xcode to create a development profile: build the generated workspace with `xcodebuild … -allowProvisioningUpdates` (or open it in Xcode once) and install with `xcrun devicectl device install app`.

## Checks

```sh
pnpm typecheck    # app + tests
pnpm test         # Jest (jest-expo): PKCE, callback validation, API client, config, reader policy, theme sync, injected annotator (jsdom), T3 prompts
```

## Security behaviour

- Tokens are stored in the Keychain via `expo-secure-store` (`WHEN_UNLOCKED_THIS_DEVICE_ONLY`, scoped to client and service). Refresh tokens rotate, and refresh runs once even when several requests trigger it. A failed refresh signs out locally.
- Sign-in uses an ephemeral browser session. The callback must match the registered redirect exactly, with exactly one matching `state` and exactly one `code`.
- API calls send the bearer only to the configured HTTPS origin, with `credentials: "omit"`, redirects refused, and no caching.
- The reader WebView has no storage or cache, CSP `default-src 'none'; script-src 'none'`, and loads only its own `about:` document. JavaScript runs only for the app's injected annotator (see above). http(s) and mailto links open in the system browser.
- A privacy cover hides content whenever the app is inactive. Sign-out clears the Keychain record and in-memory library. It doesn't sign out the web or CLI, and doesn't revoke the session at WorkOS.
